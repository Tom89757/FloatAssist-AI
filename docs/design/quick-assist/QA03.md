## 实现清单

### 通道契约

`app/src/main/java/com/dshgojava/assist/model/ModelChannel.java`

- 保留设计文档 §5 的两个核心方法：`boolean ready()` 与 `CompletableFuture<String> complete(String, List<PromptImage>, Consumer<String>)`。
- `complete` 的 `onDelta` 在 OkHttp 后台线程回调，可能调用多次；future 返回拼接后的完整文本。
- 增加默认方法 `supportsVision()`，默认返回 `false`。QA02 的 `TaskPreflight.beforeStart(..., visionSupported)` 可直接使用该值，避免未声明的通道被误判为支持读图。

`PromptImage` 沿用 QA00 已落地的本仓库 record（`mediaType` / `data` / `name`），本任务未改字段；图片数据在构造和读取时均做防御性复制。

### DirectApiModelChannel

`app/src/main/java/com/dshgojava/assist/model/DirectApiModelChannel.java`

- 直连 OpenAI 兼容的 Chat Completions 接口，无服务端会话、无历史垃圾，符合设计 §8.7。
- `Config` 字段：`baseUrl`、`apiKey`、`model`、`supportsVision`、`systemPrompt`；空白系统提示词回退到内置中文提示词。
- `ready()` 仅在 baseUrl、apiKey、model 均非空时为 `true`；未配置时 `complete` 返回失败的 future，错误种类为 `NOT_CONFIGURED`、文案为“未配置模型”。
- 地址规范化：baseUrl 可在根地址、`/v1`、完整 `/chat/completions` 三种形态间使用；统一得到 `/v1/chat/completions`（或用户给出的完整端点）。
- 请求体固定 `stream=true`，`messages` 为 system + user；无图时 user `content` 为字符串，有图时为 `text` + `image_url` 数组，图片编码为 `data:<mediaType>;base64,...`。
- 图片非空但 `supportsVision=false` 时立即失败，文案“当前模型不支持读图”，不会发出请求。
- 使用 OkHttp 异步 `enqueue`，解析、回调与错误处理都不在调用线程；默认连接超时 15s、读超时 90s、写入 30s，总 call timeout 关闭以容纳长流。
- 支持取消：future 被 cancel 时调用 OkHttp `Call.cancel()`，`onFailure` 不再覆盖已取消状态。
- SSE 响应按行增量解析，支持多行 `data:`、注释行、CRLF、BOM；`data: [DONE]` 正常结束。
- 兼容未按 SSE 返回但 HTTP 200 的 JSON 响应：解析普通 `choices[0].message.content`，通过一次 `onDelta` 回调后完成。
- 明确失败类型（`ModelException.Kind`）：`NOT_CONFIGURED`、`INVALID_CONFIG`、`VISION_UNSUPPORTED`、`HTTP`、`TRANSPORT`、`PROTOCOL`、`EMPTY_RESPONSE`；HTTP 携带状态码，并提供 `retryable()` 供 QA06 重试按钮判断。
- 隐私：不写日志；`Config.toString()` 将 apiKey 显示为 `<redacted>`；HTTP/传输错误文案会把实际 apiKey 替换为 `<redacted>`，错误体最多保留 300 字符并压成单行。

### NullModelChannel

`app/src/main/java/com/dshgojava/assist/model/NullModelChannel.java`

- `ready()` 与 `supportsVision()` 均返回 `false`。
- `complete` 直接返回 `CompletableFuture.failedFuture(new IllegalStateException("未配置模型"))`，与设计 §8.8 完全一致，不允许静默无响应。

### SSE 与 JSON 纯逻辑

`ChatSseParser.java`

- 增量解析 server-sent events；空白行派发事件，`data` 多行用换行拼接；忽略注释与未知字段；`flush()` 处理无尾随空白的流。

`ChatCompletionJson.java`

- 从流式 chunk 的 `choices[0].delta.content` 提取增量，从非流式响应的 `choices[0].message.content` 提取完整文本。
- 兼容字符串与数组形式的内容；`choices` 为空或 usage-only chunk 返回 null。
- API `error` 字段转换为显式 `ModelException(PROTOCOL)`；JSON 格式错误同样显式失败。

## 与设计文档的差异

1. 设计文档 §5 的 `ModelChannel` 只有 `ready()` 与 `complete(...)`；本实现增加默认方法 `supportsVision()`，默认 `false`。原因是降级矩阵要求“模型不支持视觉时灰显”，而 QA02 明确把视觉能力作为独立前置条件。默认值保证不会误报能力，且不破坏设计要求的两个核心方法。
2. 设计文档未定义错误类型。本实现新增 `ModelException` 与稳定 `Kind`、HTTP 状态码和 `retryable()`，便于 QA04/QA06 把错误如实展示并只重试模型调用。
3. 设计文档强调 SSE 流式；本实现对 HTTP 200 但返回普通 JSON 的兼容服务额外做一次非流式解析，仍通过 `onDelta` 回传一次完整文本，不改变流式主路径。
4. 设计文档只规定 baseUrl，未规定其形态。本实现同时接受根地址、`/v1` 和完整 `/chat/completions`，避免设置页保存不同格式时请求到错误路径。
5. 设计文档在文件清单中提到 `SessionModelChannel`，但 §3.1/§8.7 明确 P0 不引入 `dsh-client`、直连接口无会话；本任务只交付 `DirectApiModelChannel` 与 `NullModelChannel`，不创建无调用方的 Session 通道。
6. 设计文档未规定 system 提示词。本实现提供可配置 `systemPrompt`，空白时使用内置中文提示词；每次任务仍是 system + user 两条消息的无状态请求。
7. `DirectApiModelChannel.ready()` 只检查配置项非空；URL 格式错误会在 `complete` 时以 `INVALID_CONFIG` 显式失败，不在 getter 中抛异常。该选择保证设置页可以逐步填写配置。
